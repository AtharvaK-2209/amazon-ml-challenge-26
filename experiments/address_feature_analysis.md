## 1. Overview & Objectives

In entity matching, candidate pairs generated by Phase 3 blocking often exhibit high business-name similarity (e.g. "Acme Inc" vs "Acme Corp"), making string similarity on names alone insufficient to separate true entity matches from hard negatives.

The goal of **Phase 4 — Part 2 (Address Feature Engineering)** is to generate a compact, discriminative, and lightweight set of address similarity and comparison features. These features allow downstream tree classifiers (XGBoost) to resolve ambiguous candidates by evaluating address agreement, numeric/house number alignment, TF-IDF string overlap, and structured component matching.

## 2. Implemented Feature Definitions

| Feature Name | Description | Range / Values | Computation Method |
| :--- | :--- | :--- | :--- |
| `address_fuzz_ratio` | Standard RapidFuzz Levenshtein ratio | `[0.0, 1.0]` | `fuzz.ratio(a1, a2) / 100.0` |
| `address_wratio` | RapidFuzz weighted ratio (handles order/substrings) | `[0.0, 1.0]` | `fuzz.WRatio(a1, a2) / 100.0` |
| `address_token_sort_ratio` | RapidFuzz token-sorted character ratio | `[0.0, 1.0]` | `fuzz.token_sort_ratio(a1, a2) / 100.0` |
| `address_token_set_ratio` | RapidFuzz token-set intersection ratio | `[0.0, 1.0]` | `fuzz.token_set_ratio(a1, a2) / 100.0` |
| `address_jaccard` | Word token Jaccard similarity | `[0.0, 1.0]` | $|T_1 \cap T_2| / |T_1 \cup T_2|$ |
| `address_tfidf_cosine` | Word unigram + bigram TF-IDF cosine similarity | `[0.0, 1.0]` | Cosine distance on TF-IDF vectors |
| `address_char_cosine` | Character 3-gram (`char_wb`) TF-IDF cosine similarity | `[0.0, 1.0]` | Cosine distance on Char n-gram vectors |
| `address_numeric_overlap` | Jaccard overlap of extracted numeric tokens | `[0.0, 1.0]` | $|N_1 \cap N_2| / |N_1 \cup N_2|$ |
| `house_number_match` | Extracted house/building number comparison | `-1, 0, 1` | `1`: match, `0`: mismatch, `-1`: missing |
| `postal_match` | Extracted postal/PIN code comparison | `-1, 0, 1` | `1`: match, `0`: mismatch, `-1`: missing |
| `city_match` | Extracted city name comparison | `-1, 0, 1` | `1`: match, `0`: mismatch, `-1`: missing |
| `state_match` | Extracted state code comparison | `-1, 0, 1` | `1`: match, `0`: mismatch, `-1`: missing |

## 3. Conventions & Missing-Value Handling

### Comparison Conventions (`house_number_match`, `postal_match`, `city_match`, `state_match`)
To prevent misleading matches where two records simply lack address components (e.g., both missing postal codes or house numbers):
- **`1`**: Both records have non-empty parsed components AND they match exactly (case-insensitive).
- **`0`**: Both records have non-empty parsed components BUT they differ.
- **`-1`**: Either or both records are missing the address component / `None` / empty.

> **Crucial Rule**: Two missing components do **NOT** evaluate to a match (`1`). They evaluate to `-1` (missing/unknown).

### String Similarity & TF-IDF Cosine Missingness
- If either address is missing/empty/`None`, fuzzy similarities, Jaccard overlap, `address_tfidf_cosine`, and `address_char_cosine` return `0.0`.
- No `NaN` or `Inf` values are generated across any feature column.

---

## 4. Vectorizer Configuration (TF-IDF & Character N-Grams)

To ensure consistency across training, validation, and test splits without re-fitting per individual pair:

1. **Word-Level TF-IDF (`address_tfidf_cosine`)**:
   - `TfidfVectorizer(ngram_range=(1, 2), min_df=1, max_features=25000)`
   - Captures key street names, cities, and multi-word location tokens.

2. **Character N-Gram TF-IDF (`address_char_cosine`)**:
   - `TfidfVectorizer(analyzer='char_wb', ngram_range=(3, 3), min_df=1, max_features=25000)`
   - Captures character-level sub-word structure, making it robust against minor typos, suffix variations, and street abbreviations (e.g., *Street* vs *St*, *Drive* vs *Dr*).

3. **Scalable Vectorization**:
   - `AddressFeatureExtractor` fits vectorizers on unique address strings in the corpus once and precomputes sparse matrix row representations. Pairwise cosine similarity is evaluated in $O(1)$ matrix dot product lookups per candidate pair.

## 5. Real-Data Observations & Empirical Verification

Ran feature generation on a sample of **18,083 candidate pairs** generated by Phase 3 blocking on competition data:

1. **Data Quality & Integrity**:
   - **NaN Count**: `0`
   - **Inf Count**: `0`
   - **Range Compliance**: 100% compliant with specified feature bounds.

2. **Observed Feature Distributions**:
   - `address_wratio`: Mean = `0.398`, Max = `0.872` (Hard negative candidate pairs produced by blocking generally have lower address similarity than name similarity, creating high discriminative power for ML).
   - `address_char_cosine`: Mean = `0.033`, Max = `0.595` (Successfully smooths minor character differences).
   - `house_number_match`: `44.2%` missing/unparsed (`-1`), `55.7%` mismatch (`0`), `0.09%` exact match (`1`).
   - `state_match`: `66.9%` missing (`-1`), `31.8%` mismatch (`0`), `1.34%` exact match (`1`).

3. **Performance & Scalability**:
   - Evaluated **18,083 pairs** in **15.9 seconds** (~1,135 pairs/sec with full TF-IDF matrix dot products and regex parsing).

## 6. Assumptions & Limitations

1. **Address Parsing**: Component extraction utilizes `parse_address` from Phase 2 (`src/preprocessing/address_parser.py`). Regex patterns are tuned for US, India, and France formats; generic addresses fallback to 5-6 digit PIN/postal extraction and leading numeric house number matching.
2. **Open-Set Country Support**: Country comparison is handled modularly and gracefully defaults when country codes are missing.
